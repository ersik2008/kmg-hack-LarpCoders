## Модель статусов

Для соответствия ТЗ каждому требованию нужен один из трёх статусов. Сейчас такой
модели в коде нет; ниже — целевое определение, используемое в документации.

| Статус | Значение | Влияние на пайплайн |
|---|---|---|
| `PASS` | Механизм найден, доказательство получено, признаков нарушения нет | не блокирует |
| `VIOLATION` | Механизм отсутствует либо реализован некорректно, есть доказательство | **блокирует** (п. 4.3.3 ТЗ) |
| `INSUFFICIENT_EVIDENCE` | Данных для вывода недостаточно (нет релевантных файлов, анализ не завершён) | не является `PASS`; решение по нему определяется политикой |

Важно (п. 4.4.5 ТЗ): **отсутствие реализации — такое же нарушение, как
некорректная реализация.** Поэтому `VIOLATION` должен выставляться и тогда, когда
проект просто не содержит требуемого механизма, если проект относится к классу,
где механизм применим. Отличать это от `INSUFFICIENT_EVIDENCE` нужно по
применимости: библиотека без HTTP-поверхности не нарушает ИБ-02, а веб-сервис
без единой проверки токена — нарушает.

## ИБ-01

### Разграничение доступа к административному функционалу

**Формулировка ТЗ (п. 4.5.1).** Доступ к административному интерфейсу должен
предоставляться исключительно пользователям с ролью «администратор». Проверка
роли должна выполняться на стороне сервера при каждом обращении. Сокрытие
элементов административного интерфейса на стороне клиента не является
выполнением настоящего требования.

**Что необходимо проверить.**

1. Перечень серверных маршрутов, относящихся к административному функционалу
   (по пути `/admin`, по имени контроллера, по характеру операции).
2. Для каждого такого маршрута — наличие серверной проверки роли: middleware,
   декоратор, guard, явная проверка в теле обработчика.
3. Что проверка выполняется **при каждом обращении**, а не один раз при входе.
4. Что сокрытие элементов в клиентском коде не подменяет серверную проверку.
5. Маршруты, изменяющие чужие данные по идентификатору из запроса (IDOR).

**Релевантные файлы и компоненты.** Серверные маршрутизаторы и контроллеры;
middleware и guard-ы; конфигурация ролей; схема БД в части поля роли;
определения политик доступа (CASL, Casbin, accesscontrol).

**Признаки PASS.** Каждый административный маршрут защищён серверной проверкой
роли; проверка применена централизованно (guard на контроллере, middleware на
группе маршрутов) либо явно присутствует в каждом обработчике; есть сравнение
владельца ресурса с текущим пользователем там, где операция затрагивает чужие
данные.

**Признаки VIOLATION.** Административный маршрут без серверной проверки роли;
проверка только в клиентском коде (скрытие пункта меню, условный рендер);
операция `delete`/`update` по идентификатору из `req.params`/`req.body` без
сопоставления владельца; проверка роли, выполняемая один раз при входе и не
повторяемая при обращении.

**Признаки INSUFFICIENT_EVIDENCE.** В проекте не обнаружено HTTP-поверхности;
маршрутизация построена на неподдерживаемом фреймворке и не распознана; роль
задаётся внешней системой (API gateway, service mesh), конфигурация которой в
репозитории отсутствует.

**Какие сканеры помогают.** Semgrep — правила на обнаружение обработчиков без
guard-а (в текущем наборе отсутствуют, потребуется добавить). Trivy и Gitleaks
для этого требования нерелевантны.

**Где нужна LLM.** Определить, что данный маршрут относится к административному
функционалу; отличить централизованную проверку, применённую к группе
маршрутов, от её отсутствия; оценить, покрывает ли найденный guard конкретный
обработчик.

**Необходимые доказательства.** Путь к файлу, номер строки, имя обработчика,
фрагмент объявления маршрута, а также фрагмент найденного (или отсутствующего)
guard-а. Для вывода «проверка отсутствует» требуется показать объявление
маршрута и результат поиска guard-а, покрывающего этот маршрут.

**Типичные ложные срабатывания.**

* Клиентский код, скрывающий пункт меню, помечается как нарушение — тогда как
  серверная проверка присутствует в другом файле.
* Маршрут признаётся незащищённым, потому что guard применён на уровне модуля
  или контроллера, а не строкой выше обработчика.
* Публичный по замыслу маршрут (`/health`, `/login`, `/metrics`) требует роли.
* Слово `admin` в имени переменной принимается за административный маршрут.

**Рекомендации по исправлению.** Применить серверный guard или middleware к
группе административных маршрутов; для операций с чужими данными добавить
сравнение владельца ресурса; покрыть тестами случаи «без токена», «с токеном
обычного пользователя», «с токеном администратора».

**Фактическое состояние.** PARTIAL. Контроль `AUTHORIZATION`
([control-evidence.ts](../backend/src/agent/control-evidence.ts)) ищет три сигнала:

| Сигнал | Тип | Регулярное выражение (суть) |
|---|---|---|
| Проверка ролей/прав | положительный | `hasRole`, `checkPermission`, `can(`, `ability.`, `@Roles(`, `RolesGuard`, `authorize(`, `requirePermission` |
| Сравнение владельца ресурса | положительный | `ownerId`/`userId` сравнивается с `req.user`/`currentUser`/`session.user` |
| Чувствительная операция по id из запроса | отрицательный | `delete`/`remove`/`update`/`destroy` с `req.params.id` / `req.body.id` |

Ограничения текущей реализации: перечень маршрутов не строится, соответствие
«маршрут ↔ guard» не устанавливается, административные маршруты не выделяются,
клиентский и серверный код не различаются. Контроль отвечает на вопрос «есть ли
в проекте хоть какая-то авторизация», а не «защищён ли каждый административный
endpoint».

## ИБ-02

### Проверка сессии и токена на стороне сервера

**Формулировка ТЗ (п. 4.5.2).** Валидность сессии и (или) токена должна
проверяться на стороне сервера при каждом обращении к защищённым конечным
точкам, включая программные интерфейсы (API).

**Что необходимо проверить.**

1. Наличие серверного механизма аутентификации: middleware, guard, стратегия.
2. Перечень защищённых конечных точек и покрытие каждой этим механизмом.
3. Проверку срока действия токена (`exp`, `expiresIn`, `maxAge`).
4. Поведение при отсутствующем, некорректном и просроченном токене.
5. Флаги cookie (`httpOnly`, `secure`, `sameSite`), если сессия хранится в cookie.
6. Отсутствие декодирования JWT без проверки подписи.
7. Отсутствие алгоритма `none` и жёстко зашитого секрета подписи.

**Релевантные файлы и компоненты.** Модуль аутентификации; стратегии Passport и
аналоги; guard-ы; конфигурация сессий; настройки cookie; места создания и
проверки токенов.

**Признаки PASS.** Серверный middleware или guard применён ко всем защищённым
маршрутам; токен проверяется криптографически (`jwt.verify`, а не `jwt.decode`);
установлен срок жизни; секрет берётся из окружения; cookie помечены `httpOnly` и
`secure`.

**Признаки VIOLATION.** `jwt.decode` без последующей проверки подписи;
`algorithms: ['none']`; секрет подписи в исходном коде; токен без `expiresIn`;
защищённый маршрут без применённого guard-а; проверка выполняется только в
клиентском коде.

**Признаки INSUFFICIENT_EVIDENCE.** Аутентификация делегирована внешнему
провайдеру, конфигурация которого вне репозитория; HTTP-поверхность не
обнаружена.

**Какие сканеры помогают.** Semgrep — реализованные правила
`kmg-jwt-decode-without-verification`, `kmg-jwt-algorithm-none`,
`kmg-jwt-hardcoded-secret` (все `CRITICAL`); встроенный резерв —
`jwt-hardcoded-secret`.

**Где нужна LLM.** Установить, что найденный guard действительно применён к
конкретному маршруту; отличить намеренно публичный маршрут от незащищённого;
оценить достаточность механизма в целом.

**Необходимые доказательства.** Файл и строка объявления маршрута; файл и строка
применения guard-а либо доказательство его отсутствия; фрагмент кода проверки
токена; фрагмент конфигурации срока жизни.

**Типичные ложные срабатывания.**

* Проверка на фронтенде (`ProtectedRoute`, `withAuth`) принимается за серверную.
* Маршрут входа `/auth/login` или `/health` помечается как незащищённый.
* Guard, применённый через `@UseGuards` на классе контроллера, не учитывается при
  анализе отдельного метода.
* Тестовый файл с фиктивным секретом принимается за продакшн-конфигурацию.

**Рекомендации по исправлению.** Применить guard глобально с явным белым списком
публичных маршрутов; заменить `jwt.decode` на `jwt.verify` с явным списком
алгоритмов; задать `expiresIn`; перенести секрет в переменные окружения.

**Фактическое состояние.** PARTIAL. Работают два контроля.

`AUTHENTICATION` (применим только при наличии HTTP-поверхности):

| Сигнал | Тип |
|---|---|
| Стратегия/guard аутентификации (`passport.authenticate`, `PassportStrategy`, `AuthGuard`, `requireAuth`, `isAuthenticated`, `withAuth`) | положительный |
| Верификация JWT (`jwt.verify`, `verifyToken`) | положительный |
| Пакеты `passport`, `jsonwebtoken`, `@nestjs/jwt`, `next-auth`, `lucia` в манифесте | положительный |

`SESSION_MANAGEMENT`:

| Сигнал | Тип |
|---|---|
| Ограничение срока жизни (`expiresIn`, `maxAge`, `exp:`, `ttl:`) | положительный |
| Защищённые флаги cookie (`httpOnly: true`, `sameSite:`, `secure: true`) | положительный |
| Выход из аккаунта (`logout`, `signOut`, `revoke`, `destroySession`, `invalidateToken`) | положительный |
| `jwt.sign` без `expiresIn` | отрицательный |

Ограничение: покрытие конечных точек не вычисляется. Наличие `AuthGuard` в одном
файле даёт положительный признак независимо от того, применён ли guard к
остальным маршрутам.

## ИБ-03

### Защита канала передачи данных

**Формулировка ТЗ (п. 4.5.3).** Обмен данными между клиентом и сервером должен
осуществляться исключительно по протоколу TLS версии не ниже 1.2 с применением
стойких шифронаборов. Наличие конфигураций, допускающих передачу данных в
незащищённом виде либо использование устаревших версий протокола и слабых
шифронаборов, является нарушением.

**Что необходимо проверить.**

1. Конфигурацию веб-сервера и обратного прокси (nginx, Apache, Traefik, Caddy).
2. Явно заданную минимальную версию TLS и перечень шифронаборов.
3. Наличие принудительного перенаправления HTTP → HTTPS и заголовка HSTS.
4. Схемы `http://` и `ws://` в конфигурации и коде.
5. Отключение проверки сертификата (`rejectUnauthorized: false`,
   `NODE_TLS_REJECT_UNAUTHORIZED=0`, `verify=False`).
6. Разделение продакшн-, dev- и тестовой конфигураций.

**Релевантные файлы и компоненты.** `nginx.conf` и аналоги; `docker-compose.yml`;
манифесты развёртывания; конфигурация HTTP-клиентов; переменные окружения с
адресами сервисов; `frontend/Dockerfile` (в этом проекте nginx собирается
именно там).

**Признаки PASS.** В продакшн-конфигурации задан `ssl_protocols TLSv1.2 TLSv1.3`
(или эквивалент), перечень шифронаборов ограничен стойкими, настроено
перенаправление на HTTPS, проверка сертификатов нигде не отключена.

**Признаки VIOLATION.** Явно разрешены TLS 1.0/1.1 или SSLv3; слабые
шифронаборы (`RC4`, `DES`, `NULL`, `EXPORT`); продакшн-endpoint по `http://` или
`ws://`; отключённая проверка сертификата в коде, выполняющемся в продакшне;
отсутствие TLS-конфигурации в проекте, публикующем HTTP-сервис наружу.

**Признаки INSUFFICIENT_EVIDENCE.** TLS терминируется инфраструктурой, описание
которой вне репозитория (облачный балансировщик, ingress); в репозитории
присутствует только dev-конфигурация.

**Какие сканеры помогают.** Trivy `misconfig` — конфигурации Docker, Kubernetes,
Terraform. Semgrep — реализованное правило `kmg-tls-verification-disabled`
(`HIGH`).

**Где нужна LLM.** Отличить продакшн-конфигурацию от локальной; определить
назначение конкретного `http://`-адреса; оценить, является ли отсутствие
TLS-конфигурации нарушением для данного типа проекта.

**Необходимые доказательства.** Файл и строка директивы TLS либо доказательство
её отсутствия; фрагмент конфигурации; для `http://` — файл, строка и контекст,
показывающий продакшн-назначение адреса.

**Типичные ложные срабатывания.**

* `http://localhost:3000` в файле разработки помечается как нарушение.
* Ссылка `http://` внутри комментария или строки документации.
* Пространства имён XML (`http://www.w3.org/2000/svg`) принимаются за endpoint.
* Тестовая фикстура с `rejectUnauthorized: false` принимается за продакшн.

**Рекомендации по исправлению.** Задать `ssl_protocols TLSv1.2 TLSv1.3` и
ограниченный список шифронаборов; включить HSTS и редирект; убрать отключение
проверки сертификата, заменив его на доверие конкретному CA; перевести
внутренние вызовы на `https://` или явно документировать сетевую изоляцию.

**Фактическое состояние.** PARTIAL. Контроль `TRANSPORT_SECURITY` (только при
наличии HTTP-поверхности):

| Сигнал | Тип |
|---|---|
| `https://`, `createServer({ key/cert })`, `forceSSL`, `hsts` | положительный |
| `rejectUnauthorized: false`, `NODE_TLS_REJECT_UNAUTHORIZED=0`, `verify = False` | отрицательный |
| `http://` к адресу, отличному от `localhost`/`127.0.0.1`/`0.0.0.0` | отрицательный |

Встроенное исключение localhost снижает долю ложных срабатываний. Чего нет:
разбора конфигурации веб-сервера, проверки версии TLS, проверки шифронаборов,
различения продакшн- и dev-конфигурации, проверки схемы `ws://`.

## ИБ-04

### Криптографическая защита персональных данных при хранении

**Формулировка ТЗ (п. 4.5.4).** Персональные данные (фамилия, имя, отчество,
логин, адрес электронной почты, пароль) должны храниться с применением
криптографической защиты с параметрами не ниже уровня, установленного
СТ РК 1073-2007. Пароли должны храниться в виде значений функций формирования
ключа bcrypt, argon2 или scrypt. Хранение паролей в открытом виде, а равно с
применением быстрых хеш-функций общего назначения без адаптивного алгоритма,
является нарушением.

### Хранение паролей

Выделено отдельно, поскольку ТЗ задаёт закрытый перечень допустимых алгоритмов.

| Алгоритм | Допустимость по п. 4.5.4 |
|---|---|
| bcrypt | допустим |
| argon2 (argon2id) | допустим |
| scrypt | допустим |
| PBKDF2 | в перечне ТЗ отсутствует; является адаптивным KDF, требует отдельного решения экспертной комиссии |
| SHA-256, SHA-512, SHA-3, BLAKE2/BLAKE3 без адаптивного KDF | **нарушение** — быстрая хеш-функция общего назначения |
| MD5, SHA-1 | **нарушение** |
| Обратимое шифрование пароля | **нарушение** — пароль должен быть невосстановим |
| Открытый текст | **нарушение** |

Отдельно проверяются параметры: наличие соли (для bcrypt/argon2/scrypt она
встроена), достаточный фактор трудоёмкости (bcrypt cost ≥ 10, argon2 —
параметры памяти и итераций), отсутствие статической соли в коде.

**Что необходимо проверить (для требования в целом).**

1. Алгоритм хеширования пароля и его параметры.
2. Схему БД: какие поля содержат персональные данные.
3. Применение шифрования к остальным персональным данным при хранении.
4. Управление ключами: источник ключа шифрования, его длину, ротацию.
5. Режим шифрования (AEAD против ECB/CBC без контроля целостности).
6. Отсутствие вывода персональных данных в журналы.

**Релевантные файлы и компоненты.** Сервис аутентификации; модуль работы с
пользователями; схема БД и миграции; модуль шифрования; конфигурация ключей.

**Признаки PASS.** Пароль хешируется bcrypt/argon2/scrypt с адекватными
параметрами; ключ шифрования берётся из окружения или секрет-хранилища;
используется современный режим (`aes-256-gcm`); поля персональных данных либо
зашифрованы, либо явно обоснованы как не требующие шифрования.

**Признаки VIOLATION.** `createHash('md5'|'sha1'|'sha256')` применён к паролю;
сравнение пароля строгим равенством; пароль хранится как есть; ключ шифрования
жёстко задан в коде; `createCipher` без вектора инициализации; `Math.random()`
для генерации соли или токена.

**Признаки INSUFFICIENT_EVIDENCE.** Хеширование выполняется внешним провайдером
идентификации; схема БД в репозитории отсутствует; в проекте нет пользователей.

**Какие сканеры помогают.** Semgrep — реализованные правила
`kmg-weak-hash-algorithm` и `kmg-python-weak-hash-algorithm` (обе `MEDIUM`),
`kmg-insecure-randomness-for-secrets` (`HIGH`). Встроенный резерв —
`weak-crypto-md5`, `hardcoded-password`. Gitleaks и Trivy `secret` — для
обнаружения ключей шифрования в репозитории.

**Где нужна LLM.** Установить, что найденный вызов `createHash` применяется
именно к паролю, а не к контрольной сумме файла; определить, содержат ли поля
таблицы персональные данные; оценить достаточность параметров KDF.

**Необходимые доказательства.** Файл, строка и фрагмент вызова хеширования;
фрагмент схемы БД с полями персональных данных; фрагмент конфигурации ключа.

**Типичные ложные срабатывания.**

* `createHash('sha256')` для контрольной суммы файла, ETag или идемпотентного
  ключа принимается за хеширование пароля.
* Поле с именем `password` в DTO входящего запроса принимается за хранимое
  значение — на самом деле оно немедленно передаётся в `bcrypt.hash`.
* MD5 в тестовой фикстуре или в коде миграции исторических данных.
* Переменная `secret` в примере конфигурации `.env.example`.

**Рекомендации по исправлению.** Перейти на argon2id либо bcrypt с cost ≥ 12;
выполнить миграцию существующих хешей по схеме «перехеширование при следующем
успешном входе»; вынести ключи шифрования в секрет-хранилище; применить
`aes-256-gcm` вместо режимов без контроля целостности.

**Фактическое состояние.** PARTIAL. Сигналы контроля `AUTHENTICATION`:

| Сигнал | Тип |
|---|---|
| `bcrypt`, `argon2`, `scryptSync`, `scrypt(`, `pbkdf2`/`pbkdf2Sync` | положительный |
| `compare`/`verify` с аргументом, содержащим `password` | положительный |
| `password === …`, `password == …`, `storePassword(password)` | отрицательный |
| `createHash('md5'\|'sha1')` рядом со словом `password` (окно 80 символов) | отрицательный |

Сигналы контроля `CRYPTOGRAPHY`:

| Сигнал | Тип |
|---|---|
| `crypto.randomBytes`/`randomUUID`/`getRandomValues`, `secrets.token_*` | положительный |
| `aes-256-gcm`/`aes-256-cbc`, `createCipheriv`, `createDecipheriv` | положительный |
| `Math.random()` рядом со словом token/secret/key/salt/nonce/password/session | отрицательный |
| `createHash('md5'\|'sha1')`, `des-ecb`, `rc4` | отрицательный |
| `createCipher(` без IV | отрицательный |

Существенные пробелы: **SHA-256 без адаптивного KDF не детектируется как
нарушение** — отрицательный сигнал перечисляет только `md5` и `sha1`. Это прямое
расхождение с п. 4.5.4 ТЗ, который запрещает любые быстрые хеш-функции общего
назначения. Также не проверяются: параметры трудоёмкости KDF, схема БД,
шифрование остальных персональных данных, управление ключами.

## ИБ-05

### Защита локальных журналов приложения

**Формулировка ТЗ (п. 4.5.5).** Локальные журналы приложения должны храниться в
зашифрованном виде и быть защищены от модификации пользователем до момента их
отправки на сервер.

**Что необходимо проверить.**

1. Куда приложение пишет журналы локально: файл, каталог, база на устройстве.
2. Шифруется ли содержимое журнала перед записью и каким алгоритмом.
3. Как обеспечивается контроль целостности: HMAC, подпись, цепочка хешей.
4. Права доступа к файлу журнала и к каталогу.
5. Может ли пользователь приложения прочитать, изменить или удалить журнал.
6. Механизм отправки журнала на сервер и поведение до момента отправки
   (буферизация, удаление после подтверждения доставки).

**Релевантные файлы и компоненты.** Конфигурация журналирования (транспорт в
файл); модуль шифрования журналов; код установки прав доступа; код отправки
журналов; конфигурация ротации.

**Признаки PASS.** Журнал шифруется перед записью на диск; для каждой записи или
для файла вычисляется код аутентификации; права доступа ограничены владельцем
процесса; есть транспорт на сервер и удаление локальной копии после
подтверждения.

**Признаки VIOLATION.** Журнал пишется в файл открытым текстом; права доступа
позволяют запись пользователю; контроль целостности отсутствует; журнал остаётся
локально бессрочно.

**Признаки INSUFFICIENT_EVIDENCE.** Приложение не ведёт локальных журналов (пишет
только в stdout, а сбором занимается инфраструктура контейнера); конфигурация
журналирования вынесена за пределы репозитория.

**Важно.** Наличие `winston`, `pino` или `new Logger()` в проекте **не** является
выполнением ИБ-05. Требование касается шифрования и защиты от модификации, а не
факта журналирования как такового.

**Какие сканеры помогают.** Ни один из трёх подключённых сканеров такой проверки
не выполняет. Требуется собственное правило.

**Где нужна LLM.** Определить, что конкретный файловый транспорт является
локальным журналом приложения в смысле требования; оценить, применимо ли
требование к данному типу развёртывания (серверное приложение в контейнере
против клиентского приложения на устройстве пользователя).

**Необходимые доказательства.** Файл и строка конфигурации файлового
транспорта; фрагмент кода шифрования либо доказательство его отсутствия;
фрагмент кода установки прав доступа.

**Типичные ложные срабатывания.**

* Вывод в stdout контейнеризованного сервиса принимается за незащищённый
  локальный журнал — сбором занимается платформа.
* Каталог `logs/` в `.gitignore` принимается за наличие локального журнала.
* Тестовый журнал в каталоге тестов.

**Рекомендации по исправлению.** Шифровать журнал симметричным ключом,
хранящимся в защищённом хранилище платформы; вычислять HMAC по каждой записи и
связывать записи в цепочку; ограничить права `0600`; отправлять журнал на сервер
и удалять локальную копию после подтверждения.

**Фактическое состояние.** NOT IMPLEMENTED. В коде отсутствуют: контроль,
относящийся к защите журналов; сигналы, ищущие файловый транспорт; правила
Semgrep по этой теме. Контроль `AUDIT_LOGGING` относится к ИБ-07 (наличие
журналирования событий), а не к ИБ-05 (защита журнала).

**Что требуется реализовать.**

1. Сигналы обнаружения файлового транспорта: `winston.transports.File`,
   `logging.FileHandler`, `createWriteStream` с путём к `.log`,
   `RotatingFileHandler`.
2. Сигналы шифрования рядом с транспортом: `createCipheriv`, обёртки шифрования.
3. Сигналы целостности: `createHmac`, подпись записи.
4. Сигналы прав доступа: `fs.chmod`, `mode: 0o600`, `os.chmod`.
5. Правило применимости: требование применимо к приложениям, пишущим журнал на
   файловую систему; для stdout-only сервисов — `NOT_APPLICABLE` с обоснованием.

## ИБ-07

### Журналирование действий пользователей и событий СУБД (сквозное требование)

**Формулировка ТЗ (п. 4.5.7).** В проекте должен быть реализован единый журнал
действий пользователей, имеющих доступ к данным, а также журнал событий системы
управления базами данных. Журналирование должно охватывать проект в целом, а не
отдельную функцию или отдельный программный модуль. Реализация журналирования в
части функций, обеспечивающих доступ к данным, при отсутствии его в остальных,
является нарушением.

**Это сквозное требование.** Его невозможно установить по отдельно взятому файлу.
Вывод строится только по результату анализа проекта целиком.

**Что необходимо проверить.**

1. Существование **единого** механизма журналирования: middleware, интерцептор,
   аспект, централизованный сервис.
2. Полноту покрытия: перечень обработчиков, работающих с данными, и доля из них,
   охваченная механизмом.
3. Журналирование событий СУБД: журнал запросов ORM, триггеры аудита, middleware
   драйвера, настройки журналирования на стороне СУБД.
4. Состав записи аудита: кто, что, когда, над каким объектом, результат.
5. Отсутствие утечки персональных данных и секретов в журнал.
6. Защиту журнала от изменения (пересекается с ИБ-05).

**Релевантные файлы и компоненты.** Глобальные интерцепторы и middleware;
конфигурация журналирования; middleware ORM (`prisma.$use`, события Sequelize,
`SQLAlchemy event.listen`); сервисный слой; миграции с триггерами аудита;
конфигурация СУБД.

**Признаки PASS.** Найден единый механизм, применённый глобально (а не в
отдельных обработчиках); обнаружено журналирование на уровне ORM или СУБД;
покрытие обработчиков данных близко к полному; запись аудита содержит
идентификатор субъекта, действие, объект и время.

**Признаки VIOLATION.** Журналирование присутствует лишь в части обработчиков;
журнал событий СУБД отсутствует; журналируются только ошибки, без действий
пользователей; в проекте нет централизованного механизма, а есть разрозненные
вызовы `console.log`.

**Признаки INSUFFICIENT_EVIDENCE.** Журналирование вынесено в
инфраструктурный слой (service mesh, sidecar), конфигурация которого вне
репозитория; проект не работает с данными пользователей.

**Важно.** Наличие `logger.info()` в одном обработчике не является выполнением
требования. Необходимо установить существование механизма, охватывающего проект.
Симметрично: отсутствие `logger` в отдельном файле не является нарушением, если
действует глобальный middleware.

**Какие сканеры помогают.** Ни один из трёх сканеров не оценивает покрытие
проекта журналированием — это не их модель анализа. Требуется собственная
детерминированная проверка покрытия.

**Где нужна LLM.** Определить, является ли найденный механизм действительно
единым и глобально применённым; оценить, относится ли конкретный обработчик к
«функциям, обеспечивающим доступ к данным»; интерпретировать полноту покрытия.

**Необходимые доказательства.** Файл и строка регистрации глобального механизма;
перечень обработчиков данных с отметкой о покрытии; файл и строка настройки
журналирования ORM или СУБД; пример записи аудита.

**Типичные ложные срабатывания.**

* Файл без вызова `logger` помечается как нарушение, тогда как действует
  глобальный интерцептор.
* `console.log` в отладочном скрипте засчитывается как журналирование аудита.
* Журнал HTTP-запросов (`morgan`) засчитывается как журнал действий
  пользователей — он фиксирует запросы, но не субъекта и не объект операции.
* Журналирование ошибок засчитывается как журналирование действий.

**Рекомендации по исправлению.** Зарегистрировать глобальный интерцептор,
фиксирующий субъекта, действие, объект и результат; подключить middleware ORM для
журналирования операций с данными; включить журналирование на стороне СУБД;
покрыть механизм тестом, проверяющим факт записи аудита при операции с данными.

**Фактическое состояние.** PARTIAL. Контроль `AUDIT_LOGGING` применяется к любому
проекту (флаг `requiresWebSurface` не установлен):

| Сигнал | Тип |
|---|---|
| Файл `logger.*` / `logging.*` в репозитории | положительный, по пути |
| `winston`, `pino`, `bunyan`, `morgan`, `createLogger`, `new Logger(` | положительный |
| `log(ger).info/warn/error` с аргументом, содержащим login/auth/denied/forbidden/unauthorized/permission | положительный |
| `redact`, `REDACTED`, `maskSecret`, `sanitizeLog` | положительный |
| `console.log`/`info` с аргументом password/token/secret/apiKey | отрицательный |
| Пакеты `winston`, `pino`, `bunyan`, `morgan`, `@nestjs/common` в манифесте | положительный |

**Ключевое ограничение.** Сбор признаков останавливается на 8 совпадениях на
контроль (`MAX_HITS_PER_CONTROL`) и 3 на сигнал (`MAX_HITS_PER_SIGNAL`).
Соответственно, контроль отвечает на вопрос «есть ли в проекте журналирование»,
а **не** «охватывает ли оно проект целиком». Именно эту разницу п. 4.5.7 объявляет
нарушением. Кроме того, журнал событий СУБД не проверяется ни одним сигналом.

**Что требуется реализовать.**

1. Перечислить обработчики, работающие с данными (маршруты, методы сервисов,
   вызовы ORM).
2. Определить, зарегистрирован ли глобальный механизм журналирования.
3. Вычислить долю покрытых обработчиков и вынести вердикт по порогу.
4. Добавить сигналы журналирования СУБД: `prisma.$use`, `$on('query')`,
   `event.listen`, `log_statement`, `pgaudit`, триггеры аудита в миграциях.

## ИБ-08

### Контроль выгрузки персональных данных

**Формулировка ТЗ (п. 4.5.8).** Выгрузка данных, содержащих персональные
сведения, должна быть доступна исключительно пользователям с ролью
«администратор». Каждый факт выгрузки должен фиксироваться записью в журнале
аудита. Отсутствие проверки роли либо отсутствие записи в журнале аудита при
выполнении выгрузки является нарушением.

**Что необходимо проверить.** Для каждого потока выгрузки — три условия
одновременно:

1. Серверная проверка роли «администратор» на маршруте выгрузки.
2. Запись в журнал аудита при каждом факте выгрузки.
3. Достаточность содержания записи: кто выгрузил, что именно, когда, в каком
   объёме, в каком формате.

**Как обнаруживать потоки выгрузки.**

| Признак | Примеры |
|---|---|
| Маршруты | `/export`, `/download`, `/report`, `/dump`, `/backup` |
| Заголовки ответа | `Content-Disposition: attachment` |
| MIME-типы | `text/csv`, `application/vnd.ms-excel`, `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` |
| Библиотеки | `csv-writer`, `json2csv`, `exceljs`, `xlsx`, `pandas.to_csv`, `openpyxl`, `PDFKit` |
| Операции | `createWriteStream` с последующей отдачей файла; `res.download`; `res.attachment` |
| Запросы | выборка множества записей таблицы пользователей без ограничения |

**Признаки PASS.** Каждый обнаруженный поток выгрузки защищён серверной
проверкой роли администратора и сопровождается записью аудита, содержащей
субъекта, объект и время.

**Признаки VIOLATION.** Маршрут выгрузки без проверки роли; выгрузка выполняется
без записи в журнал аудита; запись аудита есть, но не содержит субъекта или
объекта выгрузки; проверка роли выполняется только в клиентском коде.

**Признаки INSUFFICIENT_EVIDENCE.** Потоков выгрузки в проекте не обнаружено;
выгрузка реализована внешним сервисом отчётности.

**Какие сканеры помогают.** Ни один из трёх сканеров не имеет правил для этого
требования. Требуется собственный набор правил Semgrep плюс детерминированный
анализ соответствия «маршрут выгрузки ↔ guard ↔ вызов аудита».

**Где нужна LLM.** Установить, что данный маршрут действительно выгружает
персональные данные, а не технический отчёт; оценить достаточность содержания
записи аудита.

**Необходимые доказательства.** Файл, строка и имя обработчика выгрузки;
фрагмент кода формирования файла; фрагмент применённого guard-а либо
доказательство его отсутствия; фрагмент вызова аудита либо доказательство его
отсутствия.

**Типичные ложные срабатывания.**

* Выгрузка технических данных (метрики, журналы сборки) принимается за выгрузку
  персональных данных.
* Клиентский код, формирующий CSV в браузере из уже полученных данных,
  принимается за серверный поток выгрузки.
* `res.download` для статического файла документации.
* Маршрут `/export` в административной панели, защищённый guard-ом на уровне
  модуля, помечается как незащищённый.

**Рекомендации по исправлению.** Объединить потоки выгрузки в один сервис;
применить к нему guard администратора; добавить обязательную запись аудита до
отдачи файла; включить в запись идентификатор субъекта, тип и объём выгруженных
данных; покрыть тестом отказ для неадминистратора и наличие записи аудита при
успешной выгрузке.

**Фактическое состояние.** NOT IMPLEMENTED. В коде нет ни контроля, относящегося
к выгрузке, ни сигналов обнаружения потоков выгрузки, ни правил Semgrep по этой
теме. Косвенно потоки выгрузки могут попасть под контроль `AUTHORIZATION`, если
обработчик содержит вызов `delete`/`update` с идентификатором из запроса, но это
совпадение, а не проверка требования.

**Что требуется реализовать.**

1. Детектор потоков выгрузки по перечню признаков выше.
2. Для каждого потока — установление факта применения guard-а администратора.
3. Для каждого потока — установление факта вызова аудита в том же обработчике.
4. Статус `VIOLATION` при невыполнении любого из двух условий, с указанием,
   какого именно.

## Дополнительные находки

Согласно п. 4.8.1 ТЗ, несоответствия Технической спецификации и прочие дефекты
безопасности приводятся в отчёте отдельным разделом и **основанием для прерывания
пайплайна не являются**.

Что агент находит сверх перечня ИБ: SQL-инъекции, command injection,
динамическое выполнение кода, XSS, path traversal, SSRF, небезопасная
десериализация, CORS с подстановочным символом при передаче учётных данных,
уязвимости зависимостей, ошибки конфигурации, секреты в репозитории.

**Расхождение с ТЗ.** В текущей реализации эти находки **влияют** на решение о
блокировке: политика работает по severity и оценке риска
([policy.service.ts](../backend/src/policy/policy.service.ts)), а не по статусам
требований ИБ. Любая находка уровня `CRITICAL` приводит к `BLOCK` независимо от
её отношения к перечню ИБ-01…ИБ-08. Подробно — [DECISION_ENGINE.md](DECISION_ENGINE.md).
