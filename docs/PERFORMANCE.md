# Производительность

Документ отвечает на требования п. 4.7 ТЗ: время выполнения шага проверки не
должно превышать 30 минут, должна обеспечиваться корректная обработка
превышения лимита и ошибок обращения к внешним сервисам.

Навигация: [README](README.md) · [ANALYSIS_PIPELINE](ANALYSIS_PIPELINE.md) ·
[LIMITATIONS](LIMITATIONS.md) · [REPRODUCIBILITY](REPRODUCIBILITY.md)

> **Измерения отсутствуют.** Замеров времени полного цикла на тестовом проекте
> не проводилось. Ниже приведены только сконфигурированные лимиты, взятые из
> кода, и методика, по которой измерения следует выполнить. Числа, выдаваемые за
> результаты бенчмарка, в этом документе отсутствуют намеренно.

---

## Ограничение сверху

| Уровень | Значение | Где задано |
|---|---|---|
| Job самопроверки | **30 минут** | `timeout-minutes: 30` в [security-scan.yml](../.github/workflows/security-scan.yml) |
| Job workflow «под ключ» | **20 минут** | `timeout-minutes: 20` в [examples/ai-security.yml](../examples/ai-security.yml) |
| HTTP-запрос из workflow | **15 минут** | `curl --max-time 900` |
| HTTP-запрос guard-а к backend | **5 минут** | `KMG_TIMEOUT_MS`, по умолчанию 300 000 мс |

Верхняя граница из ТЗ (30 минут) обеспечивается средствами GitHub Actions:
по истечении `timeout-minutes` job принудительно завершается.

## Таймауты компонентов

### Сканеры

| Сканер | Переменная | По умолчанию | Особенности |
|---|---|---|---|
| Semgrep | `SEMGREP_TIMEOUT_SECONDS` | 300 с | плюс `--timeout 30` на правило/файл (`SEMGREP_RULE_TIMEOUT`) |
| Gitleaks | `GITLEAKS_TIMEOUT_SECONDS` | 180 с | — |
| Trivy | `TRIVY_TIMEOUT_SECONDS` | 300 с | ожидание процесса `TIMEOUT + 30 с` |

Сканеры запускаются **параллельно** через `asyncio.gather`
([main.py](../security-engine/app/main.py)), поэтому теоретический максимум
этапа сканирования — время самого медленного, то есть около 330 секунд, а не
сумма всех трёх.

Превышение таймаута сканера: процесс завершается принудительно (`process.kill()`),
статус становится `FAILED` с текстом причины. Результат не интерпретируется как
«уязвимостей нет» — вердикт становится `SCAN_PARTIAL`.

### Backend

| Параметр | Переменная | По умолчанию |
|---|---|---|
| Ожидание ответа движка (полный скан) | `SECURITY_ENGINE_TIMEOUT_MS` | 600 000 мс (10 минут) |
| Ожидание ответа движка (pre-push) | `PREPUSH_ENGINE_TIMEOUT_MS` | 300 000 мс (5 минут) |
| Клонирование репозитория | жёстко задан в коде | 90 000 мс |
| Распаковка архива | жёстко задан в коде | 180 000 мс |
| Проверка готовности движка | жёстко задан в коде | 5 000 мс |

Комментарий в [scan.service.ts](../backend/src/scan/scan.service.ts) фиксирует
причину выбора 10 минут: прежний таймаут в 60 секунд прерывал нормально идущие
сканы, и каждый скан выглядел как «движок недоступен».

### Языковая модель

| Тип вызова | Таймаут |
|---|---|
| `completeJson` (триаж, контроли, цепочки, сводка) | 60 000 мс |
| `invokeToolCalling` (режим разведки) | 45 000 мс |
| `analyze` | 45 000 мс |
| Проверка ключа при старте | `GROQ_KEY_PROBE_TIMEOUT_MS`, по умолчанию 5 000 мс |

| Максимальная пауза при HTTP 429 | 300 000 мс (потолок) |

## Количество обращений к модели

Расчёт по коду, без измерений.

| Этап | Число запросов | Формула |
|---|---|---|
| Оценка контролей ИБ | 0–4 | `ceil(N / 3)`, где N — число контролей, дошедших до модели (максимум 10) |
| Цепочки атак | 0 или 1 | один запрос при наличии находок |
| Триаж находок | 0–M | `ceil(U / AI_TRIAGE_BATCH_SIZE)`, где U — число уникальных дефектов после дедупликации по `filePath::ruleId` |
| Итоговая сводка | 0 или 1 | — |
| Разведка (по умолчанию выключена) | 0 или до 3 | `AI_RECON_ITERATIONS` при `AI_RECON_ENABLED=true` |

Пример для проекта с 60 находками, сворачивающимися в 20 уникальных дефектов, и
8 контролями, дошедшими до модели:

```
контроли:      ceil(8 / 3)  = 3 запроса
цепочки атак:                 1 запрос
триаж:         ceil(20 / 3) = 7 запросов
сводка:                       1 запрос
                             ──────────
                             12 запросов
```

Аварийный ограничитель `AI_TRIAGE_MAX_FINDINGS` (по умолчанию `0` — без
ограничения) позволяет задать потолок для очень больших репозиториев.

## Объём контекста

| Что отправляется | Предел |
|---|---|
| Код в одном запросе триажа | `BATCH_CODE_BUDGET_CHARS = 12 000` символов, делится поровну между находками батча |
| Окно кода на находку, профиль «самодостаточная» | 12 строк / 1 600 символов |
| Окно кода на находку, профиль «обычная» | 22 строки / 3 500 символов |
| Окно кода на находку, профиль «поток данных» | 40 строк / 7 000 символов |
| Манифест зависимостей | 6 000 символов |
| Строка-признак контроля | 200 символов |
| Признаков на контроль | не более 8 |
| Находок в запросе цепочек атак | не более 12, файлов — не более 30 |
| Находок в запросе сводки | не более 10 |

Бюджет 12 000 символов выбран под практический лимит около 8 000 токенов на
запрос: примерно 4 символа на токен плюс место под системную инструкцию и ответ.

### Оценка расхода токенов

Ориентировочно, по объёму контекста; **не измерено**:

| Тип запроса | Порядок величины на вход |
|---|---|
| Батч триажа (3 находки) | до ~3 000 токенов (12 000 символов кода + промпт) |
| Батч контролей (3 контроля) | ~500–1 500 токенов (до 24 строк-признаков) |
| Цепочки атак | ~1 000–1 500 токенов |
| Итоговая сводка | ~500–1 000 токенов (только числа и 10 находок) |

Для примера выше (12 запросов) суммарный вход — порядка 20 000–30 000 токенов.
Это оценка по размерам структур, а не результат замера.

Почему это существенно: дневной бюджет токенов является практическим
ограничением. Комментарии в
[investigation.service.ts](../backend/src/agent/investigation.service.ts) и
[security-controls.service.ts](../backend/src/agent/security-controls.service.ts)
описывают, как именно исчерпание бюджета приводило к сканам без анализа и с
пустым графом, и какие меры (группировка, дедупликация, адаптивное окно, порядок
этапов) приняты против этого.

## Параллелизм

| Что | Состояние |
|---|---|
| Три сканера внутри движка | **параллельно** (`asyncio.gather`) |
| Запросы к модели | **последовательно** — цикл `for` по батчам |
| Сканы разных репозиториев | параллельно, каждый в своей рабочей области |
| Чтение файлов при сборе признаков | последовательно |
| Постановка скана в очередь | асинхронная: `startScan` возвращает `scanId` немедленно, конвейер выполняется в фоне |

Последовательность обращений к модели выбрана сознательно: параллельные запросы
быстрее упираются в лимит токенов в минуту.

## Кеширование

| Что кешируется | Где |
|---|---|
| База уязвимостей Trivy | предзагружается при сборке образа (`trivy image --download-db-only`), каталог `TRIVY_CACHE_DIR` |
| Правила Semgrep | вшиты в образ (`/opt/semgrep-rules` + `/app/rules`), сеть при сканировании не нужна |
| Правила Gitleaks | встроены в бинарь |
| Зависимости npm в CI | `actions/setup-node` с `cache: 'npm'` |
| Результаты сканирования | **не кешируются** — каждый скан выполняется заново |
| Индекс репозитория | **не кешируется** — строится заново каждый раз |
| Ответы модели | **не кешируются** |

Предзагрузка базы Trivy устраняет два риска сразу: задержку первого скана и
молчаливую деградацию при недоступности зеркала базы.

## Известные факторы, влияющие на время

| Фактор | Влияние |
|---|---|
| Размер репозитория | линейно на этапах Semgrep и Trivy |
| Число уникальных дефектов | линейно на числе запросов к модели |
| Состояние ключей Groq | при cooldown добавляется до 300 с ожидания на ключ |
| Доступность сети | при недоступности Groq AI-этап пропускается — скан **ускоряется** |
| Первый запуск Trivy без предзагруженной базы | загрузка базы уязвимостей |
| Размер архива | время передачи и распаковки |
| Потолок 800 файлов в `ArchitectureService` | ограничивает время построения графа на больших проектах |

## Обработка превышения лимита

### Что реализовано

| Уровень | Поведение при превышении |
|---|---|
| Сканер | процесс завершается принудительно, статус `FAILED` с причиной, вердикт `SCAN_PARTIAL` |
| HTTP-запрос backend → движок | ошибка перехватывается, все включённые сканеры получают `FAILED`, запускается резервный сканер |
| Запрос к модели | сбой этапа записывается в `stageErrors`, остальные этапы продолжаются |
| HTTP-запрос guard → backend | `AbortController` прерывает запрос; в CI — код 1 при `failOpen = false` |
| Job GitHub Actions | принудительное завершение по `timeout-minutes` |

Ни один из сценариев не превращает превышение лимита в `PASS`.

### Чего не реализовано

**Корректное завершение по п. 4.7.2 ТЗ — NOT IMPLEMENTED.**

ТЗ требует: при превышении установленного лимита времени агент должен корректно
завершить работу, сформировать отчёт в объёме выполненных проверок и вернуть код
завершения. Фактически при срабатывании `timeout-minutes` GitHub Actions job
уничтожается принудительно: отчёт в объёме выполненного не формируется, артефакт
не выгружается, код завершения не возвращается.

Что требуется реализовать:

1. Внутренний бюджет времени агента (например, 25 минут), контролируемый самим
   guard-ом или backend-ом, заведомо меньший, чем `timeout-minutes`.
2. Контроль оставшегося времени между этапами: сканирование → AI-анализ →
   формирование отчёта.
3. При исчерпании бюджета — прекращение оставшихся этапов, формирование отчёта с
   пометкой «проверка выполнена частично» и перечнем невыполненных этапов, код
   завершения в соответствии с п. 4.3.3.

**Противоречие внутри ТЗ.** П. 4.7.2 требует формировать отчёт в объёме
выполненных проверок, а п. 4.7.3 — «аварийного завершения без формирования
отчёта» при ошибках обращения к внешним сервисам. Текущая реализация ближе к
п. 4.7.2: при недоступности модели отчёт по результатам сканеров формируется, и
это представляется более полезным поведением. Расхождение с п. 4.7.3 отмечено в
[HACKATHON_COMPLIANCE.md](HACKATHON_COMPLIANCE.md).

## Методика измерения

Измерения не проводились. Ниже — воспроизводимая процедура, которой их следует
выполнить.

### Этап 1 — время работы сканеров

Движок возвращает `duration_ms` — это единственное измерение длительности,
присутствующее в системе.

```sh
curl -sS -X POST http://localhost:8000/scan \
  -H 'Content-Type: application/json' \
  -d '{"repository_path": "/abs/path/to/test-project", "scan_id": "bench-001"}' \
  | python -c "import json,sys; d=json.load(sys.stdin); print('duration_ms=%s files=%s findings=%s' % (d['duration_ms'], d['filesCount'], len(d['findings'])))"
```

Повторить не менее пяти раз, зафиксировать минимум, медиану и максимум.

### Этап 2 — полный цикл, включая AI

```sh
START=$(date +%s)
curl -sS -X POST "http://localhost:3000/api/ci/scan/summary?repository=owner/name" \
  -H "Authorization: Bearer $KMG_TOKEN" \
  -H "Content-Type: application/gzip" \
  --data-binary @/tmp/code.tar.gz \
  -o /tmp/summary.json
END=$(date +%s)
echo "полный цикл: $((END-START)) с"
python -c "import json; d=json.load(open('/tmp/summary.json')); print('файлов=%s ai=%s вердикт=%s' % (d['filesScanned'], d['aiAnalysisSucceeded'], d['verdict']))"
```

Провести два замера: с `?ai=off` и без него. Разница даёт вклад AI-этапа.

### Этап 3 — разбивка по этапам

Журнал backend содержит отметки перехода между стадиями (`CLONING`, `SCANNING`,
`ANALYZING`, `GRAPHING`, `RISK_CALCULATING`):

```sh
docker compose logs backend | grep "status changed to"
```

### Этап 4 — измерение в CI

```sh
gh run list --workflow=security-scan.yml --limit 10 \
  --json databaseId,conclusion,createdAt,updatedAt
```

### Что зафиксировать

| Показатель | Как получить |
|---|---|
| Время клонирования / распаковки | журнал backend, переход `CLONING` → `SCANNING` |
| Время работы сканеров | `duration_ms` из ответа движка |
| Время AI-анализа | разница между прогонами с `ai=off` и без |
| Время формирования отчёта | переход `RISK_CALCULATING` → завершение |
| Полное время шага в CI | длительность job-а в GitHub Actions |
| Число запросов к модели | по числу записей `ai_analyses` за скан |
| Число проанализированных файлов | `filesCount`, `filesScanned` |

### Условия, которые следует указывать при публикации результатов

Размер и состав тестового проекта (файлов, строк, языков); версии Semgrep,
Gitleaks и Trivy; модель и состояние пула ключей; включён ли AI-этап; среда
выполнения (локально или `ubuntu-latest`); холодный или прогретый кеш.
