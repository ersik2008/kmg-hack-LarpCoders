ссылку на подтверждающий файл. Статусы: `PASS`, `PARTIAL`, `NOT IMPLEMENTED`,
`UNKNOWN`.

## Критические блокеры

Перечень в порядке влияния на оценку по разделу 6 ТЗ.

### 1. Требования ИБ-01…ИБ-08 не существуют как проверяемые сущности

**Влияние:** критерий «Выявление уязвимостей» (50%) и «Полнота анализа» (5%).

Идентификаторов `ИБ-01`…`ИБ-08` нет ни в одном исходном файле. Ни отчёт, ни
вердикт, ни журнал CI не содержат статуса ни по одному требованию. Это
центральное требование ТЗ (п. 2.1.3, 4.5, 4.6.3).

**Что требуется:** реестр восьми требований, статус `PASS` / `VIOLATION` /
`INSUFFICIENT_EVIDENCE` по каждому, включение статусов в отчёт и в решение
политики.

### 2. ИБ-05, ИБ-06 и ИБ-08 не проверяются вовсе

**Влияние:** критерий «Выявление уязвимостей» (50%).

Три требования из восьми не имеют в коде ни одного механизма обнаружения. Для
ИБ-06 препятствие дополнительно техническое: файлы `.md` не читаются ни одним
компонентом анализа.

### 3. Решение о блокировке принимается по severity, а не по требованиям ИБ

**Влияние:** «Точность выводов» (10%), «Интеграция с CI/CD» (15%).

Пайплайн блокируется при любой находке `CRITICAL`, независимо от её отношения к
перечню ИБ, — при том что п. 4.8.1 ТЗ прямо указывает, что прочие дефекты
основанием для прерывания не являются. Одновременно подтверждённое нарушение
требования ИБ пайплайн не блокирует.

### 4. Отчёт не содержит сводной части по п. 4.6.3

**Влияние:** «Качество отчётности» (15%).

Отсутствуют: время начала и завершения проверки, длительность, статус по
каждому требованию. Идентификатор коммита есть только в SARIF.

### 5. Значение `paths` по умолчанию — `changed`

**Влияние:** «Полнота анализа» (5%), «Выявление уязвимостей» (50%).

Прямо противоречит п. 4.4.1 ТЗ. Исправление — изменение одной строки в
[action.yml](../action.yml).

### 6. Код завершения 2 не реализован

**Влияние:** «Интеграция с CI/CD» (15%).

Сбой инфраструктуры и нарушение безопасности неразличимы по коду завершения.

### 7. Фикстуры безопасности не подключены к автоматическому прогону

**Влияние:** «Точность выводов» (10%), «Воспроизводимость» (5%).

11 фикстур существуют, но нет ни файла ожидаемых результатов, ни исполнителя.
Доля пропусков и ложных срабатываний не измерена и не контролируется.

### 8. В корне репозитория отсутствует README.md

**Влияние:** «Воспроизводимость» (5%), а также ИБ-06 применительно к самому
проекту.

### 9. Пробелы безопасности самого агента

**Влияние:** оценка экспертной комиссией.

`git clone` через оболочку с токеном в командной строке; порт движка опубликован
наружу без авторизации; секреты по умолчанию в `docker-compose.yml`. Подробно —
[SECURITY.md](SECURITY.md#сводка-пробелов).

### 10. Отсутствие дедупликации между сканерами

**Влияние:** «Точность выводов» (10%) — дублирование находок прямо названо в
критериях оценки.

## Рекомендуемый порядок реализации

Порядок выстроен по отношению «влияние на оценку / трудоёмкость».

1. **Изменить `paths` по умолчанию на `all`** в [action.yml](../action.yml).
   Одна строка, снимает блокер №5.
2. **Создать README.md в корне репозитория** с разделом «Нормативная база»
   (перечень п. 3.1 ТЗ), кратким описанием и ссылкой на [docs/](README.md).
   Снимает блокер №8 и приводит сам проект в соответствие ИБ-06.
3. **Реализовать код завершения 2.** Разделить в `shouldFailProcess` исходы
   «проверка выполнена и выявила нарушения» и «проверка не выполнена»; доработать
   шаг проверки вердикта в workflow. Снимает блокер №6.
4. **Ввести реестр требований ИБ-01…ИБ-08.** Модуль с восемью записями:
   идентификатор, формулировка, признак сквозного характера, сигналы,
   применимость. Основание для пунктов 5–8.
5. **Добавить чтение документации и проверку ИБ-06.** Расширить список читаемых
   расширений на `.md`, `.rst`, `.txt`, `.adoc`; реализовать детерминированный
   поиск шести актов перечня п. 3.1. Наименее трудоёмкое из требований, даёт
   полноценный статус требования сразу.
6. **Реализовать проверку ИБ-08.** Детектор потоков выгрузки, установление
   наличия guard-а администратора и вызова аудита в том же обработчике.
7. **Реализовать проверку ИБ-05.** Детектор файлового транспорта журналов,
   признаки шифрования, целостности и прав доступа; правило применимости для
   stdout-only сервисов.
8. **Доработать ИБ-04.** Добавить в отрицательные сигналы любые быстрые
   хеш-функции общего назначения применительно к паролю, а не только `md5` и
   `sha1`.
9. **Доработать ИБ-07.** Перечисление обработчиков данных, определение точки
   регистрации глобального механизма, расчёт доли покрытия, сигналы
   журналирования СУБД.
10. **Доработать ИБ-01, ИБ-02, ИБ-03.** Построение соответствия «маршрут ↔
    guard» с учётом наследования от модуля и контроллера; разбор конфигурации
    TLS.
11. **Переключить политику на требования ИБ.** Расширить
    `PolicyEvaluationInput` полем `requirements`; блокировать при наличии
    `VIOLATION`; вынести прочие находки в отдельную категорию, не влияющую на
    вердикт. Снимает блокер №3.
12. **Расширить отчёт до п. 4.6.3.** Добавить `metadata` (commit, время начала и
    завершения, длительность, результат, код завершения, число нарушений) и
    раздел `requirements`. Снимает блокер №4.
13. **Реализовать Markdown-отчёт как артефакт.** Рендер того же набора данных в
    `report.md` и выгрузка через `upload-artifact`.
14. **Добавить перечень нарушенных требований в журнал CI.** Закрывает п. 4.3.5.
15. **Подключить фикстуры к автоматическому прогону.** Файл ожидаемых
    результатов, исполнитель, контроль нулевого числа находок по каталогу
    `clean/`. Снимает блокер №7.
16. **Реализовать дедупликацию находок между сканерами.** Ключ вида
    `filePath:line:категория`, единая запись с полем `detected_by`. Снимает
    блокер №10.
17. **Устранить пробелы безопасности агента.** `execFile` вместо `exec` при
    клонировании; токен вне командной строки; убрать публикацию порта 8000;
    убрать значения секретов по умолчанию из `docker-compose.yml`. Снимает
    блокер №9.
18. **Реализовать внутренний бюджет времени.** Контроль оставшегося времени
    между этапами, формирование частичного отчёта при исчерпании. Закрывает
    п. 4.7.2.
19. **Провести замеры производительности** по методике
    [PERFORMANCE.md](PERFORMANCE.md#методика-измерения) и внести результаты в
    документ.
20. **Расширить тестовое покрытие:** `toFindingRow`, `SarifService`,
    `inspectTarGz`, `safeRelativePath`, редактирование секретов, разбор ответа
    модели. Добавить запуск `kmg-guard.test.mjs` в `npm run test` и в workflow.

Пункты 1–3 выполнимы за короткое время и снимают три блокера. Пункты 4–5 дают
первый полноценный статус требования ИБ и задают образец для остальных.
