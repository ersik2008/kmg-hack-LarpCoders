## Unit-тесты

### `backend/test/scan-correctness.spec.ts` — 13 тестов

Набор проверяет корректность решения о вердикте. Название в коде —
«Mandatory Verification Suite».

| № | Проверяемое свойство | Что утверждается |
|---|---|---|
| 1 | `PASS` при нуле находок | все сканеры `COMPLETED`, находок нет → `PASS`, `riskScore = 0`, `isIncomplete = false` |
| 2 | SQL-инъекция исключает `PASS` | одна находка `CRITICAL` → `BLOCK`, `riskScore ≥ 7.0` |
| 3 | Отказ Semgrep исключает `PASS` | `semgrep = FAILED` → `result = null`, `SCAN_PARTIAL`, причина упоминает `semgrep` |
| 4 | Отказ Gitleaks исключает `PASS` | аналогично для `gitleaks` |
| 5 | Отказ Trivy исключает `PASS` | аналогично для `trivy` |
| 6 | Неготовая рабочая область исключает `PASS` | `repositoryStatus = FAILED` → `SCAN_INCOMPLETE` |
| 7 | Статус `INVALID` исключает `PASS` | сканер в состоянии `INVALID` → вердикт не выносится |
| 8 | Отказ AI не отменяет находки | детерминированные находки сохраняются, вердикт вычисляется |
| 9 | `PASS` допустим при недоступном AI | нуль находок + все сканеры `COMPLETED` → `PASS` даже без AI |
| 10 | Недоказанный поток данных → `POTENTIAL` | связь графа маркируется `POTENTIAL`, если ввод пользователя не подтверждён кодом |
| 11 | Доказанный поток данных → `CONFIRMED` | связь маркируется `CONFIRMED` при наличии ввода во фрагменте кода |
| 12 | Нет подмены репозитория фикстурами | репозиторий с `security-test` в имени не подменяется локальным корпусом; при отказе клонирования выбрасывается ошибка |
| 13 | Отозванная авторизация останавливает скан | отсутствие токена GitHub → отказ до клонирования, без анонимной попытки |

Тесты 10–13 закрывают конкретные дефекты, которые ранее приводили к
недостоверному результату — это регрессионные проверки, а не абстрактные.

### `backend/test/groq-key-pool.spec.ts` — 3 теста

| № | Проверяемое свойство |
|---|---|
| 1 | Непригодный ключ при старте пропускается, следующий рабочий помечается `healthy` |
| 2 | После ошибки аутентификации структурированный запрос повторяется со следующим ключом |
| 3 | Ключ, получивший 429, уходит в `cooldown`, работа продолжается на следующем |

### `tools/git-hooks/kmg-guard.test.mjs` — 12 тестов

Ключевой набор для соответствия требованиям CI/CD: он проверяет именно
разграничение «локально — информирование, в CI — блокировка».

| № | Сценарий | Ожидаемый код |
|---|---|---|
| 1 | `pre-push` + `PASS` | 0 |
| 2 | `pre-push` + находка `HIGH` | 0 |
| 3 | `pre-push` + находка `CRITICAL` | 0 |
| 4 | `pre-push` + вердикт `BLOCK` | 0 |
| 5 | `pre-push` + недоступный backend | 0 |
| 6 | `pre-commit` + вердикт `BLOCK` | 0 |
| 7 | `ci` + `PASS` | 0 |
| 8 | `ci` + `BLOCK` | **1** |
| 9 | `ci` + незавершённое сканирование | **1** |
| 10 | `ci` + отказ сканера при fail-closed | **1** |
| 11 | `KMG_FAIL_OPEN` разрешает только недоступную проверку, но не отменяет `BLOCK` | 1 при `BLOCK` |
| 12 | Интеграционный: настоящие git-хуки на реальном репозитории | локально 0, в CI 1 при `BLOCK` |

Тест 12 создаёт временный git-репозиторий, устанавливает в него настоящие хуки,
поднимает HTTP-заглушку KMG и выполняет реальные `git commit` и `git push` —
это не имитация, а проверка сквозного поведения.

## Фикстуры безопасности

Каталог [security-test-repository/](../security-test-repository/) содержит
11 файлов-фикстур.

```
security-test-repository/
├── README.md
├── clean/user.service.ts                       — корректный код: параметризованные
│                                                  запросы, PBKDF2
├── sql-injection/auth.service.ts               — конкатенация ввода в SQL
├── command-injection/report.service.ts         — выполнение shell с вводом
├── ssrf/webhook.service.ts                     — запрос по произвольному URL
├── xss/comment.controller.ts                   — неэкранированный вывод в HTML
├── path-traversal/file.controller.ts           — чтение произвольного пути
├── secrets/credentials.ts                      — AWS-ключи, GitHub PAT, URI БД
├── weak-crypto/hash.service.ts                 — MD5, псевдослучайные числа
├── insecure-auth/jwt.service.ts                — JWT без проверки подписи, IDOR
├── insecure-config/app.config.ts               — debug-режим, CORS «*»
└── vulnerable-dependencies/package.json        — устаревшие уязвимые библиотеки
```

**Существенное ограничение: фикстуры не подключены ни к одному автоматическому
прогону.** Поиск по репозиторию не находит упоминания `security-test-repository`
ни в тестах, ни в npm-скриптах, ни в workflow. Нет файла ожидаемых результатов,
нет исполнителя, нет сравнения фактических находок с эталоном.

Это значит: набор фикстур существует как демонстрационный материал, но
**регрессионного покрытия обнаружения не обеспечивает**. Изменение правил
Semgrep или логики нормализации не будет замечено ни одним тестом.

### Что требуется реализовать

1. Файл ожидаемых результатов, например `security-test-repository/expected.json`:
   для каждой фикстуры — ожидаемое правило, файл, диапазон строк, severity.
2. Исполнитель, запускающий движок по каталогу фикстур и сравнивающий
   фактические находки с ожидаемыми.
3. Метрики: доля обнаружений по каталогу `clean/` должна быть нулевой (контроль
   ложных срабатываний), по остальным каталогам — полной (контроль пропусков).
4. Включение исполнителя в `npm run test` и в workflow.

## Как запустить

```sh
# Backend: 16 тестов
cd backend
npm ci
npm run test

# Guard git-хуков: 12 тестов, внешних зависимостей нет
node --test tools/git-hooks/kmg-guard.test.mjs

# Покрытие backend
cd backend && npm run test:cov

# E2E — конфигурация есть, тестов нет
cd backend && npm run test:e2e
```

**Замечание по интеграции.** Набор `kmg-guard.test.mjs` **не запускается**
ни командой `npm run test`, ни workflow
[.github/workflows/security-scan.yml](../.github/workflows/security-scan.yml).
При этом именно он проверяет поведение кодов завершения — то есть наиболее
критичную для ТЗ часть. Рекомендуется добавить шаг:

```yaml
- name: Run git guard tests
  run: node --test tools/git-hooks/kmg-guard.test.mjs
```
