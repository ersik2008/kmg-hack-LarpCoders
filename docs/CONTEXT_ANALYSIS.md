# Работа с ограничением контекста модели

Документ отвечает на требование п. 4.4.4 ТЗ: при наличии ограничений на объём
контекста, передаваемого в модель, участник должен реализовать механизм,
обеспечивающий полноту анализа, и описать его.

Навигация: [README](README.md) · [ANALYSIS_PIPELINE](ANALYSIS_PIPELINE.md) ·
[LLM](LLM.md) · [SECURITY_REQUIREMENTS](SECURITY_REQUIREMENTS.md)

---

## Исходное ограничение

Используется Groq, модель по умолчанию `openai/gpt-oss-120b`
([groq.service.ts](../backend/src/ai/groq.service.ts)). Практический лимит тарифа,
зафиксированный в комментариях кода и определивший архитектуру решения, —
около **8 000 токенов на запрос** и ограниченный дневной бюджет токенов.

Прямые следствия, отражённые в коде:

* передать репозиторий одним запросом невозможно даже для небольшого проекта;
* открытый диалог с накоплением истории исчерпывал лимит за три-четыре вызова
  инструментов — это описано в комментарии к
  [investigation.service.ts](../backend/src/agent/investigation.service.ts):
  предыдущая реализация заканчивалась «без анализа, без цепочек атак и с пустым
  графом безопасности»;
* один запрос на контроль ИБ расходовал дневной бюджет до того, как начинался
  разбор самих находок — отсюда группировка по три
  ([security-controls.service.ts](../backend/src/agent/security-controls.service.ts)).

---

## Основной принцип решения

**Полнота анализа обеспечивается не языковой моделью, а детерминированными
инструментами. Модель работает только с уже найденными фрагментами.**

```
Весь репозиторий
      │
      ├──► Semgrep / Gitleaks / Trivy ───► обходят КАЖДЫЙ файл
      │                                     (ограничение контекста неприменимо)
      │
      ├──► Сборщик признаков контролей ──► обходит до 12 000 файлов,
      │                                     читает до 4 000
      │
      └──► ArchitectureService ──────────► дерево, языки, граф (до 800 файлов)
                     │
                     ▼
        Компактные структурированные результаты
                     │
                     ▼
        ┌────────────────────────────────┐
        │  В модель уходит ТОЛЬКО это:   │
        │  • строки-признаки контролей   │
        │  • окно кода вокруг находки    │
        │  • сводные числа по находкам   │
        └────────────────────────────────┘
```

Репозиторий целиком в промпт не отправляется ни на одном этапе. Это проверяемое
утверждение: все обращения к модели проходят через
`GroqService.completeJson` / `invokeToolCalling`, и содержимое каждого промпта
собирается в трёх местах — `SecurityControlsService.judgeBatch`,
`InvestigationService.triageBatch` / `buildAttackPaths` / `writeReport`,
`GroqService.explainFinding`.

| Списки файлов `all` / `readable` | [security-controls.service.ts](../backend/src/agent/security-controls.service.ts), `collectFiles` | до 12 000 в обходе, до 4 000 читаемых, глубина 8 |
| Пакеты из манифестов | там же, `readManifestPackages` | `package.json`, `requirements.txt`, `pyproject.toml`, `go.mod`, `Gemfile`, `composer.json` |

## 2. Классификация файлов

Реализовано частично.

* **По расширению:** `EVIDENCE_EXTENSIONS` (19 расширений) определяет, какие
  файлы читаются построчно; `CODE_EXTENSIONS` в Semgrep-сканере — какие файлы
  считаются исходным кодом; `SCANNABLE_EXTS` — во встроенном резерве.
* **По пути:** `fileSignals` в
  [control-evidence.ts](../backend/src/agent/control-evidence.ts) распознают
  lock-файлы, `.env`, приватные ключи, конфигурацию dependabot/renovate,
  security-workflow — по одному лишь имени, без чтения содержимого. Сделано
  намеренно: lock-файл может весить мегабайты, а факт его существования уже
  является доказательством.
* **По роли в архитектуре:** `MODULE`/`CONTROLLER`/`SERVICE`/`MODEL`/`DATABASE`/
  `EXTERNAL_API`/`CONFIG`/`FILE` — в `ArchitectureService`.

**Не классифицируются:** документация (`.md` не входит ни в один список),
тестовые файлы и фикстуры (кроме исключения `.spec.`/`.test.` при построении
графа), продакшн- против dev-конфигурации.

## 3. Оценка релевантности

**NOT IMPLEMENTED в форме скоринга.** Вместо числовой оценки релевантности
применяется бинарный отбор по срабатыванию сигнала: файл попадает в контекст
контроля тогда и только тогда, когда в нём сработало регулярное выражение этого
контроля. Такой отбор даёт точную привязку `file:line`, но не ранжирует файлы и
не выбирает «самые важные» при превышении лимита — вместо этого действуют жёсткие
потолки `MAX_HITS_PER_SIGNAL = 3` и `MAX_HITS_PER_CONTROL = 8`.

Для находок сканеров релевантность заменена сортировкой по severity и
дедупликацией по ключу `filePath::ruleId`
([investigation.service.ts](../backend/src/agent/investigation.service.ts),
`selectForTriage`).

## 4. Контекст под конкретное требование

**NOT IMPLEMENTED для ИБ-01…ИБ-08** — требований как сущностей в коде нет.

**Реализовано для 10 контролей.** Каждый контроль имеет собственный набор
сигналов, и контекст собирается независимо для каждого. Пример для
`AUTHENTICATION`:

```
Контроль AUTHENTICATION
  ├── packages: passport, bcrypt, argon2, jsonwebtoken, next-auth, lucia, @nestjs/jwt
  ├── сигнал «Стойкое хеширование пароля»  → до 3 совпадений file:line
  ├── сигнал «Проверка пароля»             → до 3 совпадений
  ├── сигнал «Стратегия/guard»             → до 3 совпадений
  ├── сигнал «Верификация JWT»             → до 3 совпадений
  ├── сигнал «Пароль без хеширования»      → до 3 совпадений  (отрицательный)
  └── сигнал «Быстрый хеш для пароля»      → до 3 совпадений  (отрицательный)
                                              ────────────────
                                              всего не более 8
```

## 5. Разбиение на части

| Уровень | Механизм | Параметр |
|---|---|---|
| Контроли | группировка по 3 контроля на запрос | `CONTROL_BATCH_SIZE = 3` |
| Находки | группировка по N находок на запрос | `AI_TRIAGE_BATCH_SIZE`, по умолчанию 3 |
| Код внутри батча | общий бюджет, режется поровну | `BATCH_CODE_BUDGET_CHARS = 12 000` |
| Окно вокруг находки | адаптивное, три профиля | 12/1600, 22/3500, 40/7000 (строк/символов) |
| Цепочки атак | не более 12 находок и 30 файлов в одном запросе | — |
| Итоговая сводка | не более 10 ключевых находок | — |

Адаптивный размер окна (`contextBudget`) — существенная деталь: «самодостаточные»
находки (секрет, `ws://`, слабый хеш) решаются по одной строке, находки о потоке
данных (инъекции, SSRF, traversal) требуют увидеть источник ввода. Расход токенов
привязан к тому, что действительно нужно для вердикта.

Отдельный случай: находка в lock-файле получает **манифест** зависимостей вместо
фрагмента lock-файла (`readDependencyManifest`). Иначе модель могла ответить
только «недостаточно данных» — по строке lock-файла невозможно судить о
достижимости уязвимого кода.

## 6. Анализ по файлам

Реализован детерминированными средствами: Semgrep, Gitleaks и Trivy обходят
рабочую область самостоятельно и не ограничены контекстом. Каждый файл, попавший
под расширения соответствующего инструмента, анализируется.

Модель пофайловый анализ не выполняет — она видит только окна вокруг уже
найденного.

## 7. Кросс-файловый анализ

Реализован частично и только на уровне графа атак:
`InvestigationService.buildAttackPaths` получает до 12 находок из разных файлов и
строит связи между точками входа и опасными операциями. Связь, ссылающаяся на
файл, которого нет в списке находок, отбрасывается.

**NOT IMPLEMENTED:** межпроцедурный анализ потоков данных, разрешение
`import`/`require` между модулями, построение реального call graph. Связи графа
атак опираются на описания находок, а не на прослеженный поток данных, и поэтому
маркируются `CONFIRMED` либо `POTENTIAL`.

## 8. Агрегация промежуточных результатов

```
Запрос 1 (контроли A, B, C) ──► 3 assessment
Запрос 2 (контроли D, E, F) ──► 3 assessment      ──► таблица security_controls
Запрос 3 (контроли G, H)    ──► 2 assessment

Запрос 4 (цепочки атак)     ──► до 8 рёбер        ──► graph_edges

Запрос 5 (находки 1–3)      ──► 3 вердикта
Запрос 6 (находки 4–6)      ──► 3 вердикта        ──► ai_analyses (finding_triage)
…                                                      + копирование на дубликаты

Запрос N (итоговая сводка)  ──► Markdown          ──► ai_analyses (finding_analysis)
```

Между запросами ничего не накапливается: каждый вызов независим, история не
пересылается. Сбой одного запроса не уничтожает результаты остальных — ошибка
попадает в `outcome.stageErrors`, а обработка продолжается.

## 9. Финальный синтез моделью

`InvestigationService.writeReport` получает **только сводные данные**: общее число
находок, распределение по severity, число уникальных дефектов, счётчики
подтверждённых и ложных срабатываний, число связей графа, перечень сбоев этапов и
до 10 ключевых находок с их вердиктами. Код в этот запрос не передаётся.

Результат — Markdown с разделами «Общая оценка», «Ключевые риски», «Что исправить
в первую очередь», «Ограничения проверки». Он сохраняется в `ai_analyses` и
отображается в интерфейсе. **На вердикт политики не влияет.**

## 10. Сохранение доказательств

| Этап | Что сохраняется | Куда |
|---|---|---|
| Находка сканера | `filePath`, `startLine`, `endLine`, `codeSnippet`, `ruleId`, `scanner` | таблица `findings` |
| Признак контроля | `filePath`, `line`, `snippet`, `note` | `security_controls.evidence` (JSON) |
| Вердикт триажа | `verdict`, `confidence`, `reason`, `exploitation`, `recommendation` | `ai_analyses.metadata` |
| Связь графа атак | `filePath`, `line`, `reason`, `confidence` | `graph_edges.metadata` |

Секреты не сохраняются: Gitleaks запускается с `--redact`, а нормализатор
принудительно ставит `codeSnippet: "***REDACTED***"` для находок Gitleaks и для
секретов Trivy.

## Маршрут «требование → вывод»

Схема из задания применительно к тому, что есть в коде. Строки, где написано
«NOT IMPLEMENTED», обозначают отсутствующее звено.

```
Требование ИБ-XX                       NOT IMPLEMENTED (сущности требования нет)
        │
        ▼
Релевантные файлы                      PARTIAL — отбор по срабатыванию сигнала
        │                                        контроля, не по требованию
        ▼
Релевантные символы                    NOT IMPLEMENTED (карты символов нет)
        │
        ▼
Фрагменты контекста                    PASS — file:line + строка кода,
        │                                     ≤3 на сигнал, ≤8 на контроль
        ▼
Анализ                                 PASS — пачка из 3 контролей в один запрос
        │
        ▼
Промежуточные выводы                   PASS — ControlAssessment на контроль
        │
        ▼
Кросс-файловая агрегация               PARTIAL — только граф атак по находкам
        │
        ▼
Итоговый вывод                         PARTIAL — статус контроля, не требования
```

Для сравнения, тот же маршрут для находки сканера реализован полностью:

```
Находка Semgrep/Gitleaks/Trivy
        │
        ▼  filePath + startLine
Определение профиля контекста (contextBudget)
        │
        ▼  12/22/40 строк либо манифест зависимостей
Формирование батча (≤3 находки, ≤12 000 символов кода)
        │
        ▼
Вердикт модели: TRUE_POSITIVE | FALSE_POSITIVE | UNCERTAIN + confidence
        │
        ▼  фильтр по id батча
Сохранение + копирование вердикта на дубликаты (filePath::ruleId)
        │
        ▼
Удаление рёбер графа, опиравшихся на ложные срабатывания
```

## Сквозные требования

### Почему анализа изменённых файлов недостаточно

Требование считается сквозным, когда соответствие ему обеспечивается общим
компонентом проекта. Формально: вывод зависит от наличия или отсутствия
механизма **где-то** в проекте, а не от содержимого конкретного файла.

Отсюда две симметричные ошибки, обе возникающие при анализе только диффа.

**Ложное срабатывание.** Изменён файл `orders.controller.ts`, в нём нет вызова
`logger`. При анализе только диффа это выглядит как нарушение ИБ-07. В
действительности в проекте зарегистрирован глобальный интерцептор
журналирования, покрывающий все контроллеры, — но его файл не менялся и в дифф
не попал.

**Пропуск.** Коммит удаляет одну строку в `app.module.ts` — регистрацию
глобального guard-а аутентификации. Дифф из одного файла; ни один обработчик не
изменился. При анализе только диффа нарушение ИБ-02 масштаба всего проекта
остаётся незамеченным: сигнатуры маршрутов прежние, а защита снята.

Эта же логика — обоснование п. 4.4.1 и 4.4.2 ТЗ.

### Какие требования являются сквозными

| ID | Почему сквозное | Что нужно видеть целиком |
|---|---|---|
| ИБ-07 | Требует **единого** механизма, охватывающего проект. Явно назван сквозным в п. 4.5.7 | все обработчики данных + точка регистрации механизма + конфигурация ORM/СУБД |
| ИБ-02 | Guard регистрируется один раз, защищает все маршруты | точка регистрации + полный перечень маршрутов |
| ИБ-01 | Роль проверяется централизованно; административные маршруты разбросаны | перечень админ-маршрутов + точки применения guard-ов |
| ИБ-08 | Потоки выгрузки распределены по модулям; guard и аудит могут быть в других файлах | все потоки выгрузки + guard-ы + вызовы аудита |
| ИБ-03 | Конфигурация TLS лежит вне кода приложения | конфигурация веб-сервера, прокси, развёртывания |

ИБ-04, ИБ-05 и ИБ-06 локализуемы: хеширование пароля, конфигурация журнала и
текст документации находятся в конкретных файлах. Но и они не будут найдены, если
эти файлы не изменялись в коммите.

### Состояние в коде

Полный обход поддерживается тремя из четырёх путей запуска — см.
[ANALYSIS_PIPELINE.md](ANALYSIS_PIPELINE.md#full-project-analysis). Значение по
умолчанию `paths: changed` в [action.yml](../action.yml) противоречит п. 4.4.1 и
вынесено в критические пробелы.

Оценка контролей ИБ **всегда** выполняется по всей рабочей области: сборщик
признаков обходит дерево самостоятельно и не знает о том, какие файлы
изменялись. То есть при полном обходе сквозная часть анализа работает корректно;
при `paths: changed` в рабочую область попадает только дифф, и сборщик признаков
видит лишь его.

## Что требуется реализовать

Перечень с конкретными шагами; порядок — в
[HACKATHON_COMPLIANCE.md](HACKATHON_COMPLIANCE.md).

1. **Реестр требований.** Модуль с восемью записями: идентификатор, формулировка,
   признак сквозного характера, набор детерминированных сигналов, профиль
   релевантных файлов.
2. **Отбор файлов под требование.** Для каждого требования — предварительная
   выборка по расширению, пути и сигналам; результат — упорядоченный список
   кандидатов с оценкой релевантности.
3. **Оценка покрытия для ИБ-07.** Перечисление обработчиков данных, определение
   точки регистрации глобального механизма, расчёт доли покрытия, вердикт по
   порогу.
4. **Соответствие «маршрут ↔ guard» для ИБ-01, ИБ-02, ИБ-08.** Построение списка
   маршрутов, определение применённых к ним guard-ов с учётом наследования от
   модуля и контроллера.
5. **Чтение документации для ИБ-06.** Добавление `.md`/`.rst`/`.txt`/`.adoc` в
   читаемые расширения и детерминированный поиск шести актов перечня п. 3.1.
6. **Агрегация по требованию.** Сведение промежуточных выводов в один статус
   `PASS` / `VIOLATION` / `INSUFFICIENT_EVIDENCE` с обязательным перечнем
   доказательств.
7. **Переключение значения по умолчанию** `paths` на `all` в
   [action.yml](../action.yml).
